- # EPIC 3 — Authorization (RBAC)
    - ## Epic Scope
    - Workspace-scoped Role-Based Access Control.
    - Authorization is permission-key driven.
    - Every workspace member has exactly one role.
    - Every role contains a set of permission keys.
    - Authorization must be centrally enforced.
    - 
    - ## Feature 3.1 — Permission Catalog
    - ### User Story
    - As the system, I want a centralized permission registry so that access control is consistent.
    - ### Services / Actions Used
        - **Service:** `PermissionRegistryService`
    - ### Domain Rules
        - Permission keys must be unique.
        - Keys must follow dot notation (e.g., `task.assign`).
        - Permissions are global definitions (not workspace-scoped).
        - Roles reference permissions.
    - ### Tasks
        - **DB**
            - `permissions` table:
                - id
                - key (unique)
                - description
                - timestamps
        - **Seed**
            - workspace.*
            - member.*
            - role.*
            - project.*
            - task.*
            - comment.*
            - audit.*
            - report.*
        - **Tests**
            - duplicate permission key fails
    - 
    - ## Feature 3.2 — Role Management
    - ### User Story
    - As an admin, I want to create and manage roles so that I can control permissions inside my workspace.
    - ### Services / Actions Used
        - **Action:** `CreateRole`
        - **Action:** `UpdateRole`
        - **Action:** `DeleteRole`
        - **Action:** `SyncRolePermissions`
        - **Service:** `RoleService`
        - **Service:** `AuthorizationService`
    - ### Domain Rules
        - Roles are workspace-scoped.
        - System roles (if defined) cannot be deleted.
        - A role assigned to members cannot be deleted unless reassigned.
        - Role names must be unique within workspace.
    - ### Tasks
        - **DB**
            - `roles`:
                - id
                - workspace_id
                - name
                - is_system
                - timestamps
            - `role_permissions`:
                - role_id
                - permission_id
                - unique(role_id, permission_id)
        - **API**
            - GET /roles
            - POST /roles
            - PATCH /roles/{id}
            - DELETE /roles/{id}
            - PUT /roles/{id}/permissions
        - **Implementation**
            - `RoleService::create(...)`
            - `RoleService::delete(...)`
            - `RoleService::syncPermissions(...)`
        - **Tests**
            - cannot delete role assigned to members
            - unique role name enforced
            - permission sync works
    - 
    - ## Feature 3.3 — Permission Enforcement
    - ### User Story
    - As the system, I want permission checks centralized so that security rules are consistent.
    - ### Services / Actions Used
        - **Service:** `AuthorizationService`
    - ### Domain Rules
        - Permission checks must not be duplicated in controllers.
        - All permission resolution must go through AuthorizationService.
        - Membership must exist before permission resolution.
    - ### Tasks
        - Implement `AuthorizationService::hasPermission(user, permissionKey)`
        - Resolve:
            - membership
            - role
            - permissions
        - Integrate with Laravel Gate or custom middleware
        - Protect all workspace routes with permission middleware
        - Tests for allow/deny scenarios
